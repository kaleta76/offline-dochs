## Architecture rules
- Terminal button mapping lives in `src/lib/terminal-actions.ts`; cache only its validated projection per account/organization and retain newest accepted version, while all actions use the existing enqueue path — configuration must not change offline punch durability or cache employee plans.
- Attendance identity uses the existing SAP string identifier, never names/email; column grants block legacy profile identity and raw audit payload reads, while cache sanitization preserves offline records — display-only masking is insufficient pseudonymization.
- Each account belongs to one immutable organization via profiles; roles stay in user_roles and all RLS/RPC authorization checks organization equality — prevents cross-company access and keeps offline queued user IDs unambiguous.
- Company signup is provisioned atomically by the auth lifecycle trigger; joining requires a rotatable private organization invitation and grants employee only — client metadata never chooses existing tenancy or privileges.
- Organization reference data is stored in organization_settings, organization_codes and organization_holidays; legacy tables are provisioning templates only — company admins cannot alter another company's payroll configuration.
- Attendance math lives only in `src/lib/engine.ts` as a pure function with tests in `engine.test.ts`; UI and exports call it, never reimplement it — keeps payroll results consistent.
- Punches are written to the IndexedDB queue (`src/lib/offline-queue.ts`) first and synced with an idempotent `client_uuid` — offline is a core requirement.
- Server time, drift and SHA-256 hash chain are set by the `punches_chain` DB trigger, never by the client — tamper evidence must not depend on the device.
- Punches are append-only; corrections become new punches only via the `decide_correction` RPC — audit trail stays intact. The single exception is `delete_test_organization` / `purge_organization` (migration 0007, `docs/ZRUSENIE-TESTOVACEJ-ORGANIZACIE.md`): an admin may delete a whole organization, and only one that is flagged `is_test` and is not the original organization; never widen it to unflagged organizations or to single punches.
- Offline app shell is generated by TanStack SPA prerender and precached with vite-plugin-pwa after all build environments; the single registration wrapper refuses dev/preview and supports sw=off — prevents stale editor previews.
- Synchronization is scoped to the authenticated owner, sends nothing while the local queue is empty, reads the session locally, never repeats an insert flagged `server_inserted`, and deletes local punches only after a select (or, after a transport failure only, the `verify_punch_synced` RPC) confirms the exact payload; certificate errors pause automatic retries and backoff resets on online/manual triggers — keeps strict corporate networks quiet without losing punches.
- Údaje o účte po prihlásení (roly, profil, organizácia) sa čítajú len cez `loadMe` v `src/lib/me-profile.ts` (jeden POST dopyt, RPC `get_my_profile`); pôvodné čítania so `select=` sú len záloha pri chýbajúcej funkcii (PGRST202), nie pri chybe spojenia. Nové čítania po prihlásení pridávaj ako malé RPC s pevnými stĺpcami, nie ako `select=` — firemný proxy (Fortinet) blokuje niektoré GET dopyty so `select=` a POST prechádza.
- Cache profile data by user ID and restore after hydration; cached roles are display hints only, with database RLS authoritative — prevents shared-device leakage.
- Inactivity sign-out lives only in `src/lib/idle-timeout.ts` (throttled `last_activity_at`, pending flag blocks protected routes until the next sign-in); it ends the session and account cache only and never touches the IndexedDB punch queue — shared devices stay protected without losing punches.
- Device verification is decided only by the punches_chain trigger, which hashes the raw device key server-side and discards it; device state changes go through security-definer RPCs that write audit_log — clients can never mark their own punches verified. The device recovery code is never shown to the user and there is no "recovery code" button (it let an employee move the verified status to another device without a manager); a lost or cleared device is replaced through "Nahradiť pôvodné zariadenie" and manager approval — see `docs/OVERENIE-ZARIADENI.md`.
- Registrácia firiem a zamestnancov ide výlučne cez server funkcie v `src/lib/accounts.functions.ts` (logika v `accounts-core.ts`, dokumentácia `docs/REGISTRACIA.md`): firma sa zakladá stálym registračným kódom (v repozitári len odtlačok), zamestnanec dostane jednorazový PIN od správcu, e-mail sa nezbiera. Nevracaj `supabase.auth.signUp`, e-mailové potvrdenie ani ukladanie PIN-u v čitateľnej podobe — prvé by obišlo registračný kód, druhé by vrátilo problém s doručením pošty a osobné údaje.

## Integrácia s dochádzkovým systémom (Access) – pravidlá pre agenta

Terminál odovzdáva razenia lokálnemu dochádzkovému systému. Rozhranie je definované v `contract/` a **nemení sa bez výslovného pokynu vlastníka**. Dokumentácia: `docs/SPOLUPRACA.md`.

1. Pred prácou na exporte, tabuľke `punches`, tabuľke `profiles` alebo mapovaní osobných čísel si prečítaj `contract/README.md` a `docs/SPOLUPRACA.md`.
2. `contract/` nemeň (ani zlatý súbor), pokiaľ úloha výslovne nehovorí o zmene kontraktu. Ak ho zmena schémy rozbije, **zastav sa a napíš, čo sa rozbije**, neprepisuj test, aby prešiel.
3. Referenčná implementácia exportu je `contract/reference/punch-export.ts`. Keď sa export zavedie do aplikácie, ide o jej kópiu v `src/lib/punch-export.ts`. Kontraktový test `contract/tests/punch-export.contract.test.ts` musí prechádzať.
4. Vzorec hash reťaze v `punches_chain` nemeň. Ak je zmena nevyhnutná, ide o novú hlavnú verziu kontraktu.
5. Cieľový stav (zatiaľ neimplementované, nemeň to bez pokynu): razenie je fakt a terminál ho **vždy prijme**, uzavretie mesiaca rieši lokálny dochádzkový systém. Kým to vlastník výslovne nezadá, platí súčasné správanie (`month_closures`).
6. Do exportov, logov ani obrazoviek nedávaj mená ani e-maily. Zamestnanec je identifikovaný len osobným číslom SAP.
7. Nové migrácie opíš v PR: čo mení v `punches`/`profiles` a či to ovplyvní export.
8. Ak úloha mení export, `punches` alebo `profiles`, spusti `bun run lint`, `bun run test`, `bun run build` a napíš, čo si nemohol overiť.
9. História sa neprepisuje (žiadny force-push, žiadny rebase publikovaných commitov).
10. Rob len to, čo úloha žiada. Každý zásah do nesúvisiacich súborov stojí vlastníka kredity.
11. Priečinok `access/` je dochádzkový systém v Accesse (VBA a inštalátor), vyvíja ho Claude mimo Lovable. Lovable agent ho nemení; súbory v ňom sa nesmú prekonvertovať (inštalátor overuje SHA-256 po bajtoch).
